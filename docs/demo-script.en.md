# Demo video script (target 2 min 40 s, hard limit 3 min)

**Language:** 🇬🇧 English ｜ [🇨🇳 中文](demo-script.md)

> ⚠️ **Decide the narration language before you record.** This is a JAPAC-regional competition and the reviewing panel may not understand Mandarin. This file is the English-narration version; `demo-script.md` is the Chinese-narration version, with an identical storyboard. **Recommendation: English voiceover with burned-in bilingual subtitles** — narrate in the reviewers' language while keeping Chinese subtitles so you can verify the numbers yourself. If you record in Mandarin, English subtitles are mandatory, otherwise language becomes a non-technical scoring loss.

> Official requirement: the demo video must be **under 3 minutes**. Write the storyboard before recording — it is faster than cutting footage afterwards.
>
> **Recording strategy**: the differentiators of this project are (a) the AI **fetching its own data via tools** and (b) **carbon-aware scheduling**. Both must be *visible on screen*. The tool-call trace has to be in frame and the carbon curve has to be pointed at. Showing only "the AI wrote a paragraph" would throw away the easiest technical points to win.

## Pre-recording checklist

- [ ] The service is deployed to Cloud Run and you have a publicly reachable URL
- [ ] `GEMINI_API_KEY` is configured as a Cloud Run secret and the page shows "generated by gemini-2.5-flash calling tools autonomously"
- [ ] **Confirm the "AI tool-call trace" section is populated.** If it says "offline mode, no tool calls", the key is not active — fix that first
- [ ] Browser zoom at 110%, address bar and bookmarks bar hidden (`Cmd+Shift+B`)
- [ ] All notifications off (Do Not Disturb)
- [ ] Click "Analyse" once beforehand and record the response time; if it exceeds 20 s, plan to record first and trim the wait

## Storyboard

| Time | On screen | Voiceover (English, read as written) |
|---|---|---|
| 0:00–0:15 | Static on the landing page | "We run multi-cloud GPU clusters. The most common waste isn't a broken card — it's **cards that are reserved but not being used**. Conventional monitoring tells you the utilisation number. It never tells you what that waste costs, or which item to fix first." |
| 0:15–0:30 | Click "Load sample data and analyse" | "That's the missing step we built. The input comes from a monitoring export: reserved cards, cards actually used, duration, average utilisation — and the hour the load runs." |
| 0:30–0:50 | Four metric cards appear | "Over one window: X GPU-hours wasted, equivalent to ¥X of electricity, X kWh of energy, and X kilograms of CO₂e." (**Read the real numbers on screen; do not memorise a script**) |
| 0:50–1:20 | Scroll to the grid carbon-intensity curve | "But carbon has a dimension people rarely look at: **when** you run. This curve is the grid's carbon intensity across 24 hours. Lowest at the midday solar peak, highest during the evening fossil ramp — a spread of over 30%. Which means **the same energy, the same electricity bill, and lower carbon just by moving the workload to another hour**." |
| 1:20–1:50 | Scroll to the AI tool-call trace | "Here's the key design: **the AI doesn't generate numbers — it calls tools to fetch them**. It calls `query_metrics` for the detail, `simulate_defer` to compute the carbon saved by shifting the hour, and `propose_action` to register each recommendation in the decision list. What you see is every single call — every number is traceable to a tool return value." |
| 1:50–2:15 | Scroll to the decision list, click "Accept" on one item | "So the output isn't a report — it's a **decision list**: auto-reclaim idle nodes, recover over-reservations, move the heaviest node to a lower-carbon hour. Each one carries an expected cost recovery and an expected carbon reduction. I click Accept, and the totals update live." |
| 2:15–2:30 | Point at the carbon total | "Note the last one: shifting the hour saves no money, but it does save carbon. Eliminating waste and shifting the window are two independent decarbonisation paths, and we account for them separately." |
| 2:30–2:40 | Back to the metric cards | "This is the GPU Compute Waste Auditor: turning numbers nobody reads into energy and carbon decisions you can schedule." |

## Editing notes

- **Numbers must be real**: every number spoken must match the recorded screen. Reviewers will compare them.
- Do **not** speed up the tool-call trace section — let the viewer read the tool names and arguments.
- Do not add background music over the narration; voice takes priority.
- Burn in subtitles (auto-captions are unreliable for technical terms like `query_metrics`).
- Hold a static final frame for 2 seconds; do not cut to black abruptly.

## Fallback material (if time allows)

- Show the layering diagram from `docs/architecture.md` and stress the "deterministic compute + AI decision" trade-off — this earns technical points.
- **Demonstrate the offline fallback**: with no API key the page still runs, the tool trace reads "offline mode, no tool calls", and the decision list is still produced by rules. This proves the system is not a chat-bot wrapper but has real engineering fallbacks.
- Show the `/api/carbon-profile` JSON response to prove the carbon curve is a first-class, externally consumable interface rather than decorative charting.

## Trim order if you run over time

1. Drop 0:15–0:30 (the data-source explanation) and fold it into the previous voiceover
2. Then drop 2:15–2:30 (the two-paths explanation), keeping the shot but halving the narration
3. **Never cut** the carbon-curve section or the tool-trace section — those are where this project scores
