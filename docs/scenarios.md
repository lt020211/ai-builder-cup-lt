## 0. 一句话定位

> **把一段训练失败的日志，变成带着证据链的根因判断 —— 并明确回答那个最要命的问题：
> 「这是代码的锅，还是该换卡？」**

分诊器的输出不是报告，是**两个可以直接拿去行动的结论**：

1. **六分类**：application / hardware / hardware_watch / environment / config / network / undetermined
2. **是否报修**（`should_rma`）：一个布尔值

值班模式下还多一步：**它自己发现、自己止损、自己建单、自己通知人**（见第 4 节）。

## 1. 为什么这两个结论值钱

一线有一对**方向相反的典型误判**，公开的集群运维资料反复在讲同一件事：

| 误判 | 表现 | 代价 |
|---|---|---|
| **把应用 bug 当硬件故障** | 看到 Xid 13 / 31 / 43 就去报修 | 一块好卡被下线、走 RMA 流程、集群容量白掉 |
| **把硬件劣化当偶发** | 看到 Xid 94 就说「重启一下就好」 | 劣化持续累积，直到 Xid 95 出现时影响面已经扩大 |

这两种误判**用同一个错误码就能触发**。所以判别依据不能是码本身，只能是：

- **趋势**（30 天内频次是否上升、可纠正 ECC 是否同步上升）
- **是否跟随任务移动**（换节点仍复现 → 指向应用；不跟随 → 指向硬件）
- **因果链**（Xid 45 是 Xid 48 的次生事件，把它当根因就会查错方向）
- **内核与进程状态**（有 Xid 62 / 进程处于 D 状态 → 查驱动；零 Xid / futex 等待 → 查代码）

**这几件事正是 AI 该上场的地方，也是规则引擎做不到的地方** —— 第 3 节的 F8 用可复现的实验证明了这一点。

## 2. 适用场景

### 2.1 核心场景（已全部实现并覆盖案例）

| ID | 场景 | 触发时刻 | 使用者 | 典型输入 | 期望输出 | 依赖工具 | 对应案例 |
|---|---|---|---|---|---|---|---|
| **S1** | **启动即挂**：环境 / 版本不兼容 | 秒级 | AI 工程师 | 报错文本 + 驱动/CUDA/torch 版本 | 「环境不兼容」+ 具体升降哪一项 | `check_compat` | `case-driver-old` |
| **S2** | **跑到一半 OOM** | 分钟–小时 | AI 工程师 | OOM 报错 + 训练配置 | 「配置问题，硬件是好的」+ 理论显存 + 改哪个参数 | `estimate_memory` | `case-oom-batch` / `case-oom-fragmentation` |
| **S3** | **看到 Xid，判断要不要报修** | 任意 | 一线运维 | dmesg 片段 | **是否报修** + 依据 | `lookup_xid` + `inspect_node` | `case-xid48-dbe` / `case-xid79-bus` |
| **S4** | **集合通信超时 / 卡死** | 分钟 | 一线运维 | NCCL 超时文本 | 「超时是次生现象，根因在链路」 | `search_failure_signature` + `inspect_node` | `case-nccl-nvlink` |
| **S5** | **同一个 Xid 反复出现** | 天–周 | 平台团队 | 30 天历史 | 「偶发观察」vs「劣化超限，走 RMA」 | `inspect_node`（趋势） | `case-xid94-single` ↔ `case-xid94-rising` |
| **S6** | **不知道是代码还是硬件** | 任意 | 一线运维 | 任意报错 | 六分类 + 置信度 | 全部工具的组合 | `case-illegal-access` / `case-segv` 类 |
| **S7** | **驱动掉了**：nvidia-smi 无法与驱动通信 | 秒级 | 一线运维 | `nvidia-smi` 报错 + dmesg | **是内核模块问题还是掉卡** | `search_failure_signature` + `inspect_node` | `case-driver-nvml-mismatch` ↔ `case-smi-driver-dead` |
| **S8** | **GPU 卡死**：训练不动、利用率却满格 | 分钟–小时 | 一线运维 | 卡死现象 + 内核 Xid + 进程状态 | **是应用死锁还是驱动/硬件挂死** | `inspect_node` + `lookup_xid` | `case-gpu-hang-xid62` ↔ `case-gpu-hang-deadlock` |

**S7 与 S8 是症状最吓人、但根因跨度最大的两个场景**，也是最能体现「分诊」价值的地方：

- **S7 的坑**：「nvidia-smi 无法与驱动通信」有**五种**常见成因 —— 内核升级后模块未重编 /
  Secure Boot 拦截未签名模块 / 驱动包未带 DKMS 模块 / 装错模块变体 / **GPU 掉出 PCIe 总线**。
  **只有最后一种是硬件故障**，而它的修法与其他四种完全不同（重装驱动永远修不好）。案例库里
  `case-driver-nvml-mismatch` 与 `case-smi-driver-dead` 两句报错几乎一模一样，结论却相反。
- **S8 的坑**：同样是「训练卡死」，判别依据是**内核是否干净**与**进程是否处于 D 状态**。
  有 Xid 62 / D 状态阻塞 → 查驱动；零 Xid / S 状态 futex 等待 → 查代码。
  案例库 `case-gpu-hang-xid62` 与 `case-gpu-hang-deadlock` 构成对照。

### F8 详解：为什么这是最值钱的一项功能

评审 40% 的权重压在「技术质量与 Gen AI 实现」上。而**证明 Gen AI 在这里是必需的**，
比声称它有用要有力得多。

做法：

1. 对案例库全部 **14 个**案例，跑一遍**纯规则路径**（本地、秒级、不用模型），输出准确率；
2. 每个案例可单独跑一次 **AI 分诊**，结果缓存；
3. 并排展示对比，并**指出规则基线错在哪几个、为什么错**。

**实测结果**（`node scripts/verify_triage.mjs`，可直接复跑）：

```
规则基线准确率（分类 + 是否报修全对）：11 / 14　（78.6%）
  仅看分类：11 / 14　仅看是否报修：12 / 14
```

| 案例 | 期望 | 规则给出 | 规则读不出的东西 |
|---|---|---|---|
| `case-xid48-dbe` | hardware + 报修 | application | Xid 45 是「前序错误的后果」，把它当根因会查错方向 |
| `case-xid94-rising` | hardware + 报修 | hardware_watch | 与 `case-xid94-single` 同一个码、同一张卡型，判别依据不是码本身，而是趋势与是否跨应用扩散 |
| `case-gpu-hang-deadlock` | application | network | 与 `case-gpu-hang-xid62` 同样是「训练卡死」，判据是内核是否干净、进程是否为 D 状态 |

**这个对比本身就是「为什么需要 Gen AI」的可复现证据。** 而且它是可被评委当场复现的：
同一个页面，点一下就能跑（本地秒出、不消耗配额）。这比任何 PPT 论证都硬。

> ⚠️ **诚实性约束**：基准表的数字必须来自**实际运行**。跑出来是 11/14 就写 11/14，并说明那三题错在哪。
> **伪造准确率是最容易被现场戳穿的事。** AI 分诊那一侧的数字不由人填 —— 页面跑满 14 个案例后自动统计，
> 未跑满就显示为空。

## 4. 执行层：三级风险、分级审批与**真实执行**

> 这是本项目对「AI 能不能自动修」这个问题的正面回答。
> **答案是：低风险它可以自己动手，而且动手是真的；中高风险它把门槛降到最低，但把决定留给人。**

### 4.1 先把架构约束讲清楚

本应用是**纯静态站点**，没有后端。而这恰恰意味着两件事：

1. **它没有任何途径碰你的生产集群。** 真实算力在腾讯云 / 阿里云 / 百度云 / 智星云，
   与 Google Cloud 之间没有网络通路，架构上也够不着。**迁移的只是方法论，不是数据。**
2. **「执行是真的」必须另有办法证明。** 如果「执行」只是界面上把按钮变灰、把文案改成「已处理」，
   那它和一份 PPT 没有区别，评委一眼就能看穿。

所以做法是：放一个**有真实状态的模拟集群后端**（Cloud Firestore），
让 Agent 的动作真的落库、真的回读、真的留痕：

| 集合 | 用途 |
|---|---|
| `cluster` | 6 个模拟节点（`cordoned` / `schedulable` / `draining` / `jobs` / `telemetry`…） |
| `events` | **操作日志**：`before` → `fields_written` → `after` → `verified` |
| `tickets` | 工单草稿（`status: 'draft'`） |
| `notifications` | 通知队列（`status: 'queued'`） |

评委可以在 Firebase 控制台里刷新 `cluster` 集合，亲眼看到数据变了 ——
**这是「执行是真的」唯一的证明方式。**

> ⚠️ 安全规则是**匿名可读写**（浏览器端没有登录流程）。这是明确的安全边界，不是疏漏：
> 开放面被规则锁死在 4 个集合内，其余路径一律拒绝；**生产部署必须换成基于 Auth 的规则。**

### 4.2 三级风险

| 风险级 | 判定规则 | 审批要求 | 数量 | 例子 |
|---|---|---|---|---|
| **低** | 只影响当前任务进程、可逆、不碰硬件与系统 | **一键批量批准**（★ 且**系统可自主执行**） | **6** | 调 microbatch / 开重计算 / 加 `PYTORCH_CUDA_ALLOC_CONF` / 重启任务进程 / **cordon** |
| **中** | 影响节点上其他任务，或需要短暂中断 | **逐条批准** + 勾选影响面确认 | **5** | 重载 nvidia 内核模块 / 重启节点 / GPU 复位 / 对齐驱动版本 / 驱逐节点 |
| **高** | 不可逆、涉及硬件资产、跨节点或影响他人 | **逐条批准** + **必须填变更单号与审批人** + 二次确认 | **3** | 提交 RMA / 下线某张卡 / 批量升级驱动 |

判定看的是**爆炸半径**，不是难易：**装个 wheel 可能很麻烦，但它只影响一个容器，所以是低风险；
重启节点只是敲一行命令，但它会杀掉别人跑了一周的任务，所以是中风险。**

**★ 为什么 Agent 自主执行的第一条动作是 `cordon_node`**：它只挡新任务、**不打断任何正在运行的任务**、
且完全可逆。面对疑似硬件劣化，正确顺序是**先 cordon、再观察、最后才决定要不要 drain** ——
因为 cordon 可逆，而打断别人跑到一半的任务不可逆。

### 4.3 ★ 关键设计：风险等级不从模型来

动作库里每个动作**自带** `risk` 字段，模型只能**选用**（传 `action_id`），不能**自定**等级。

```js
// tools.js: execute_action —— 只有 low 会被真正执行
if (act.risk !== 'low') return { refused: true, error: '…你无权直接执行。',
                                instead: '请用 propose_fix 登记…交给人工审批流' };
```

这样模型就无法「说服」系统把一个高风险动作降级成低风险、绕过审批。
**这是反幻觉设计向执行层的延伸** —— 与「数字必须来自工具」是同一条纪律。

**★ 两个容易做反的细节，都已经在代码里定死**：

1. **安全规则优先于可用性检查。** 风险检查排在「有没有连接集群」之前 ——
   否则模型收到的是「没有连接集群」，会以为连上再试一次就行了，把审批门槛误读成环境问题。
   **审批是规则，规则必须先说。**
2. **`TOOL_PARAMS` 白名单同时是安全边界。** 模型偶尔会多传参数（**甚至试图传一个 `risk` 来给动作重新定级**），
   不在白名单里的字段连进都进不来。

### 4.4 怎么判定「执行真的生效了」

`cluster.js` 的 `EFFECTS` 表里，**每个动作必须给出三样东西，缺一不可**：

```js
cordon_node: (n) => ({
  fields: { cordoned: true, schedulable: false },                    // 真的会落库
  verify: (a) => a.cordoned === true && a.schedulable === false,     // 拿什么判定它生效
  describe: `禁止 ${n.node} 接新任务；节点上 ${(n.jobs||[]).length} 个正在运行的任务未受影响`,
}),
```

**没有 `verify` 的动作不允许被登记** —— 因为「执行了但没验证」等于没执行，只是换了个地方写日志。
执行链路是：

```
before → planned.effect() → patchNode（真的写 Firestore）→ 读回 after → verify(after) → 写 events
```

回验失败时事件写 `unverified`，界面显示「回验未通过」。
**宁可显示一条失败的动作，也不要谎报成功** —— 演示里的假成功，
在评委追问一句「数据真的变了吗」时就会崩。

### 4.5 报修只建草稿，不提交

`file_rma` 是高风险：走一次 RMA，集群就少一块卡。所以 `draft_ticket` 只建 `status: 'draft'` 的工单，
把证据、命令、判断依据全填好，让**人只需要点确认**。草稿里
`approved` / `ticket_no` / `approver` 三个字段**只能由人填写** —— 那是人签字的痕迹。

**低风险它自己动手，高风险它把门槛降到最低但把决定留给人。** 这是产品判断力，不是能力缺失。

### 4.6 输出：执行包

审批完成后由浏览器生成并下载，包含：

1. 分诊结论与证据链（每条结论指回 `T1` / `T3` 这样的引用编号）
2. 逐条动作 + **可复制命令** + **预期输出**（用于执行后验证）
3. **回滚步骤** —— 每个动作都必须有，**没有回滚方案的动作不允许进执行包**
4. 审批记录：谁批的 / 何时 / 变更单号
5. 未获批准的动作明确标注 **「未批准，请勿执行」**

第 3 条和第 5 条是这份文件存在的理由：一份执行包里最危险的东西，
不是写错的命令，而是**没被批准却被执行**的命令。

## 5. 明确不做的事（以及原因）

| 不做 | 原因 |
|---|---|
| 接入实时监控 API（DCGM / Prometheus）、接入真实生产集群 | 本应用是纯静态站，没有后端；且需要生产凭据。与生产集群之间没有网络通路 |
| **不自动执行中高风险动作** | 见 4.3。低风险它自主执行；中高风险一律拒绝执行并引导去人工审批 |
| **不代替人提交报修** | 报修是不可逆的资源决策，按下提交键这件事必须由人来做 |
| **不假装通知已经发出去了** | 通知落到 `notifications` 集合、状态保持 `queued`；真实部署需接 IM / 邮件 |
| **不假装有常驻服务** | 值班巡检由人点一下开始、之后自动跑完；真实部署应由 Cloud Scheduler 定时触发。界面上写清楚了 |
| 训练日志全文解析 | 大文件解析需要后端；只解析报错段落与关键行 |
| 多租户 / 权限体系 | 超出本次范围（但审批流的字段结构已按可扩展设计） |
| **覆盖全部 100+ 个 Xid 码** | 只收 **24 条**常见且能从官方文档核实的（另有 **27 条**故障特征签名）。**其余如实返回「知识库无记录，不得推测」** |

最后一条不是偷懒，是设计。**知识库的边界就是模型的能力边界** ——
查不到就必须说查不到。这条纪律本身就是「AI 不编造」最直观的演示。

## 6. 与上一版（GPU 算力浪费审计器）的关系

| | 上一版 | 本版 |
|---|---|---|
| 视角 | **成本** 视角：找出浪费了多少钱 | **可靠性** 视角：救活跑挂的任务 / 揪出坑你的卡 |
| 核心输出 | 优化动作 + 回收金额 | **是否报修** + 六分类 |
| AI 的角色 | 编排工具做审计与归因 | 编排工具做**判别与因果推断**，值班模式下还**真的动手** |
| 数据可信度 | 自造数据集（软肋） | 知识库逐条带官方文档 URL，评委可自行核对 |
| 与 2025 APAC 冠军 SalesShortcut 的关系 | 方向重合（都是「省」） | **零重合**；四步结构（发现 → 取证 → 判断 → 处置+触达）对齐但领域不同 |

**保留下来的资产**（与领域无关，整个搬过来了）：Firebase Hosting 纯 REST 发布链路、
AI Logic 工具调用循环（含 `role=user` 回传、模型降级链、两种 429 的区分处理、
跨模型续跑）、离线降级设计、以及「三个验收脚本各挡一类 bug」的方法论。

## 7. 术语

| 术语 | 含义 |
|---|---|
| **Xid** | NVIDIA 驱动检测到 GPU 异常时写入内核日志的错误码。**不是累计计数，是「最近一次事件的码值」** —— 要看历史必须查 dmesg / journald |
| **RMA** | Return Merchandise Authorization，硬件返修流程。走一次意味着集群少一块卡 |
| **contained / uncontained** | A100 之后引入的错误隔离能力：Xid 94 只影响单个应用，Xid 95 会跨应用扩散 |
| **row remapping** | HBM 上把坏行重映射到备用行。重映射失败（Xid 64）意味着备用行耗尽 |
| **GSP** | GPU System Processor。Xid 119 / 120 指向固件与驱动软件栈，不是显存报废 |
| **ZeRO stage** | 数据并行组内逐级切分模型状态：0 不切 / 1 切优化器 / 2 再切梯度 / 3 连参数一起切 |
| **cordon / drain** | 调度器里的两个不同动作：cordon **只挡新任务**、不打断在跑的；drain **会驱逐**在跑的任务。本项目的判据是前者可逆、后者不可逆 |
| **回验（verified）** | 执行动作后**重新读回服务端状态**来确认改动生效。没生效就写 `unverified`，不谎报成功 |
| **引用编号（`T1`…）** | 工具真正执行时登记的编号，让每条结论可以指回产生它的那次调用 |
