# 适用场景与功能规格

**语言：** [🇬🇧 English](scenarios.en.md) ｜ 🇨🇳 中文

> 本文是「训练故障分诊器」的功能边界说明书。写它的目的只有一个：
> **在动手之前把「做什么」和「不做什么」都钉死**，避免做到一半才发现场景没覆盖、
> 或者承诺了 4 天做不完的东西。
>
> 提交截止 2026-10-18。本文件的场景分级（核心 / 延伸 / 产品化）就是排期依据。

---

## 0. 一句话定位

> **把一段训练失败的日志，变成带着证据链的根因判断 —— 并明确回答那个最要命的问题：
> 「这是代码的锅，还是该换卡？」**

分诊器的输出不是报告，是**两个可以直接拿去行动的结论**：

1. **六分类**：application / hardware / hardware_watch / environment / config / network / undetermined
2. **是否报修**（`should_rma`）：一个布尔值

---

## 1. 为什么这两个结论值钱

一线有一对**方向相反的典型误判**，公开的集群运维资料反复在讲同一件事：

| 误判 | 表现 | 代价 |
|---|---|---|
| **把应用 bug 当硬件故障** | 看到 Xid 13 / 31 / 43 就去报修 | 一块好卡被下线、走 RMA 流程、集群容量白掉 |
| **把硬件劣化当偶发** | 看到 Xid 94 就说「重启一下就好」 | 劣化持续累积，直到 Xid 95 出现时影响面已经扩大 |

这两种误判**用同一个错误码就能触发**。所以判别依据不能是码本身，只能是：

- **趋势**（30 天内频次是否上升、可纠正 ECC 是否同步上升）
- **是否跟随任务移动**（换节点仍复现 → 指向应用；不跟随 → 指向硬件）
- **因果链**（Xid 45 是 Xid 48 的次生事件，把它当根因就会查错方向）

**这三件事正是 AI 该上场的地方，也是规则引擎做不到的地方。**

## 2. 适用场景

### 2.1 核心场景（提交前必须做完）

| ID | 场景 | 触发时刻 | 使用者 | 典型输入 | 期望输出 | 依赖工具 |
|---|---|---|---|---|---|---|
| **S1** | **启动即挂**：环境 / 版本不兼容 | 秒级 | AI 工程师 | 报错文本 + 驱动/CUDA/torch 版本 | 「环境不兼容」+ 具体升降哪一项 | `check_compat` |
| **S2** | **跑到一半 OOM** | 分钟–小时 | AI 工程师 | OOM 报错 + 训练配置 | 「配置问题，硬件是好的」+ 理论显存 + 改哪个参数 | `estimate_memory` |
| **S3** | **看到 Xid，判断要不要报修** | 任意 | 一线运维 | dmesg 片段 | **是否报修** + 依据 | `lookup_xid` + `inspect_node` |
| **S4** | **集合通信超时 / 卡死** | 分钟 | 一线运维 | NCCL 超时文本 | 「超时是次生现象，根因在链路」 | `search_failure_signature` + `inspect_node` |
| **S5** | **同一个 Xid 反复出现** | 天–周 | 平台团队 | 30 天历史 | 「偶发观察」vs「劣化超限，走 RMA」 | `inspect_node`（趋势） |
| **S6** | **不知道是代码还是硬件** | 任意 | 一线运维 | 任意报错 | 六分类 + 置信度 | 全部工具的组合 |
| **S7** | **驱动掉了**：nvidia-smi 无法与驱动通信 | 秒级 | 一线运维 | `nvidia-smi` 报错 + dmesg | **是内核模块问题还是掉卡** | `search_failure_signature` + `inspect_node` |
| **S8** | **GPU 卡死**：训练不动、利用率却满格 | 分钟–小时 | 一线运维 | 卡死现象 + 内核 Xid + 进程状态 | **是应用死锁还是驱动/硬件挂死** | `inspect_node` + `lookup_xid` |

**S7 与 S8 是症状最吓人、但根因跨度最大的两个场景**，也是最能体现「分诊」价值的地方：

- **S7 的坑**：「nvidia-smi 无法与驱动通信」有**五种**常见成因 —— 内核升级后模块未重编 /
  Secure Boot 拦截未签名模块 / 驱动包未带 DKMS 模块 / 装错模块变体 / **GPU 掉出 PCIe 总线**。
  **只有最后一种是硬件故障**，而它的修法与其他四种完全不同（重装驱动永远修不好）。案例库里
  `case-driver-nvml-mismatch` 与 `case-smi-driver-dead` 两句报错几乎一模一样，结论却相反。
- **S8 的坑**：同样是「训练卡死」，判别依据是**内核是否干净**与**进程是否处于 D 状态**。
  有 Xid 62 / D 状态阻塞 → 查驱动；零 Xid / S 状态 futex 等待 → 查代码。
  案例库 `case-gpu-hang-xid62` 与 `case-gpu-hang-deadlock` 构成对照。

### 2.2 延伸场景（有余力就做）

| ID | 场景 | 价值 | 难度 |
|---|---|---|---|
| **S9** | **批量归因** | 运维每周真的要干这件事：一批失败任务里找共性根因 | 中 |
| **S10** | **节点体检** | 巡检场景：给一个节点出健康结论 + 待办清单 | 低 |
| **S11** | **证据不足时如实说不知道** | 不是场景而是纪律：宁可输出 `undetermined`，也不猜 | 低（但必须做） |

> S11 值得单列。分诊器最大的风险不是判错，而是**看起来很确定地判错**。
> 所以工具在查不到记录时会明确返回「无记录，不得推测」，界面也会把
> `undetermined` 渲染成正常的、被尊重的输出，而不是失败。

### 2.3 产品化方向（只在 deck 里讲，本次不实现）

| ID | 方向 | 为什么只讲 |
|---|---|---|
| **P1** | 监控系统 webhook 自动分诊 | 需要常驻后端与生产凭据；本应用是纯静态站 |

### F8 详解：为什么这是最值钱的一项功能

评审 40% 的权重压在「技术质量与 Gen AI 实现」上。而**证明 Gen AI 在这里是必需的**，
比声称它有用要有力得多。

做法：

1. 对案例库全部 **14 个**案例，跑一遍**纯规则路径**（本地、秒级、不用模型），输出准确率；
2. 每个案例可单独跑一次 **AI 分诊**，结果缓存；
3. 并排展示对比，并**指出规则基线错在哪几个、为什么错**。

预期结果（这是设计目标，不是既成事实，实测后如实填写）：

| 路径 | 预期准确率 | 错在哪（预判） |
|---|---|---|
| 纯规则基线 | 约 11–12 / 14 | 会错在**必须读趋势**（Xid 94 偶发 vs 频次上升）与**必须辨因果链**（Xid 45 是次生、48 才是根因）的案例上；可能还有「症状相同、根因相反」那两组里的一条 |
| AI 分诊 | 14 / 14 | —— |

**这个对比本身就是「为什么需要 Gen AI」的可复现证据。** 而且它是可被评委当场复现的：
同一个页面，点一下就能跑。这比任何 PPT 论证都硬。

> ⚠️ 诚实性约束：基准表的数字必须来自**实际运行**。跑出来是 9/10 就写 9/10，
> 并说明那一条错在哪。伪造准确率是最容易被现场戳穿的事。

## 4. 执行层：三级风险与分级审批

> 这是本项目对「AI 能不能自动修」这个问题的正面回答。**答案是：能出方案，但不越过人来动手。**

### 4.1 先讲清一个架构约束

本应用是**纯静态站点**，没有后端。而部署在 Google Cloud 的后端也**够不着你的集群** ——
你的算力在腾讯云 / 阿里云 / 百度云 / 智星云，与 Google Cloud 之间没有网络通路。

所以「AI 直接执行修复」在本项目里**架构上不可能实现**。但更重要的是：

> **这条路本来就不该走。**
>
> 1. 评委席上坐的都是 Google Cloud 工程师，他们会立刻问「你凭什么让 AI 直接改我的生产集群」；
> 2. 真实运维流程本来就是「AI 出方案 → 人工审批 → 变更单 → 执行」，跳过审批反而是减分项；
> 3. 让 AI 自动改驱动、自动提交 RMA，在生产环境是反模式。
>
> **主动不执行，是工程判断力，不是能力缺失。**

### 4.2 三级风险

| 风险级 | 判定规则 | 审批要求 | 例子 |
|---|---|---|---|
| **低** | 只影响当前任务进程、可逆、不碰硬件与系统 | **一键批量批准** | 调 microbatch / 开重计算 / 加 `PYTORCH_CUDA_ALLOC_CONF` / 重启任务进程 |
| **中** | 影响节点上其他任务，或需要短暂中断 | **逐条批准** + 勾选影响面确认 | 重载 nvidia 内核模块 / 重启节点 / GPU 复位 / 对齐驱动版本 / 驱逐节点 |
| **高** | 不可逆、涉及硬件资产、跨节点或影响他人 | **逐条批准** + **必须填变更单号与审批人** + 二次确认 | 提交 RMA / 下线某张卡 / 批量升级驱动 / 重置 NVSwitch |

### 4.3 ★ 关键设计：风险等级不从模型来

动作库里每个动作**自带** `risk` 字段，模型只能**选用**（传 `action_id`），不能**自定**等级。

这样模型就无法「说服」系统把一个高风险动作降级成低风险、绕过审批。
**这是反幻觉设计向执行层的延伸** —— 与「数字必须来自工具」是同一条纪律。

### 4.4 修复动作库（节选）

| action_id | 动作 | 风险 | 回滚 |
|---|---|---|---|
| `set_expandable_segments` | 开启显存可扩展段 | 低 | unset 该环境变量 |
| `reduce_micro_batch` | 降低 microbatch | 低 | 改回原值 |
| `enable_gradient_checkpointing` | 开启梯度重计算 | 低 | 改回原值 |
| `restart_job` | 重启任务进程 | 低 | —— |
| `align_torch_wheel` | 换成与驱动匹配的 torch wheel | 低 | 装回原 wheel |
| `reload_nvidia_modules` | 重载 nvidia 内核模块 | 中 | 重启节点 |
| `reboot_node` | 重启节点 | 中 | —— |
| `gpu_reset` | 复位指定 GPU | 中 | —— |
| `align_driver_version` | 对齐节点驱动版本 | 中 | 回退驱动 |
| `drain_node` | 驱逐节点上的任务 | 中 | 取消驱逐 |
| `file_rma` | 提交硬件报修 | 高 | 撤回工单 |
| `retire_gpu` | 下线该卡 | 高 | 重新上线 |
| `bulk_driver_upgrade` | 批量升级驱动 | 高 | 逐节点回退 |

**另有一条被系统标记为「不建议」的动作**：`raise_nccl_timeout`（调大集合通信超时）。
知识库明确写着它是**掩盖问题而非解决问题** —— 动作库保留它但标记 `discouraged`，
界面上灰显、不可直接选中。**这是系统有主见的地方，也是很好的演示点。**

### 4.5 输出：执行包

审批完成后由浏览器生成并下载，包含：

1. 分诊结论与证据链（每条结论指回 `T1` / `T3` 这样的引用编号）
2. 逐条动作 + **可复制命令** + **预期输出**（用于执行后验证）
3. **回滚步骤** —— 每个动作都必须有，没有回滚方案的动作不允许进执行包
4. 审批记录：谁批的 / 何时 / 变更单号
5. 未获批准的动作明确标注 **「未批准，请勿执行」**

## 5. 明确不做的事（以及原因）

| 不做 | 原因 |
|---|---|
| 接入实时监控 API（DCGM / Prometheus） | 本应用是纯静态站，没有后端；且需要生产凭据 |
| **不自动执行修复**（但提供分级审批 + 执行包） | 见第 4 节。AI 出方案、人审批、导出可落地的执行包；不越过人直接改环境 |
| 训练日志全文解析 | 大文件解析需要后端；只解析报错段落与关键行 |
| 多租户 / 权限体系 | 超出本次范围 |
| **覆盖全部 100+ 个 Xid 码** | 只收 **24 条**常见且能从官方文档核实的（另有 **27 条**故障特征签名）。**其余如实返回「知识库无记录，不得推测」** |

最后一条不是偷懒，是设计。**知识库的边界就是模型的能力边界** ——
查不到就必须说查不到。这条纪律本身就是「AI 不编造」最直观的演示。

## 7. 术语

| 术语 | 含义 |
|---|---|
| **Xid** | NVIDIA 驱动检测到 GPU 异常时写入内核日志的错误码。**不是累计计数，是「最近一次事件的码值」** —— 要看历史必须查 dmesg / journald |
| **RMA** | Return Merchandise Authorization，硬件返修流程。走一次意味着集群少一块卡 |
| **contained / uncontained** | A100 之后引入的错误隔离能力：Xid 94 只影响单个应用，Xid 95 会跨应用扩散 |
| **row remapping** | HBM 上把坏行重映射到备用行。重映射失败（Xid 64）意味着备用行耗尽 |
| **GSP** | GPU System Processor。Xid 119 / 120 指向固件与驱动软件栈，不是显存报废 |
| **ZeRO stage** | 数据并行组内逐级切分模型状态：0 不切 / 1 切优化器 / 2 再切梯度 / 3 连参数一起切 |
