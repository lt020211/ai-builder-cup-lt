# 架构说明

## 1. 问题定义

多云 GPU 集群里最普遍的浪费不是「卡坏了」，而是**预留与使用的错配**：

| 模式 | 现象 | 现有监控能不能发现 |
|---|---|---|
| 超额预留 | 申请 8 卡，实际只跑 4 卡，另 4 卡全程占位 | 能，但没人天天看 |
| 长期空转 | 卡被占用，平均利用率 < 5% | 能，但缺上下文 |
| 低效运行 | 利用率 5%~30% 之间，长期不收敛 | 难，需要跨周期对比 |

传统监控只回答「现在利用率多少」，不回答**「这些浪费值多少钱、该先动哪个、动了能省多少」**。本项目补的就是这一步。

## 2. 数据流

```
监控平台导出（云 / 节点 / 卡型 / 预留卡数 / 使用卡数 / 时长 / 平均利用率 / 起始时段）
        │
        ▼
┌─────────────────────────┐
│  analyzer.py  纯计算层  │  浪费卡时 → 电耗 → 电费 → 碳排，并判定浪费模式
│  无网络、无 AI 依赖     │  ← 可独立单元测试，结果可复算
└─────────────────────────┘
        │  结构化审计结果（summary + findings + records）
        ▼
┌─────────────────────────┐
│  carbon.py  碳强度模型  │  24 点电网碳强度曲线 → 「什么时候跑最省碳」
│  纯函数，无副作用       │  ← 电耗不变、电费不变，只挪时段即可减碳
└─────────────────────────┘
        │
        ▼
┌──────────────────────────────────────────────┐
│  ai.py  AI 决策层（工具调用循环）             │
│                                              │
│   模型 ──functionCall──▶ tools.py            │
│    ▲                      │                  │
│    └──functionResponse────┘                  │
│         （最多 8 轮，见 MAX_TOOL_TURNS）     │
│                                              │
│  工具：query_metrics / estimate_carbon /     │
│        simulate_defer / propose_action       │
│  无密钥或调用失败 → 降级为离线规则模板       │
└──────────────────────────────────────────────┘
        │
        ▼
  Flask Web（Cloud Run）→ 指标卡 + 碳曲线 + 工具轨迹 + 决策清单
```

**分层原则**：所有数字由 `analyzer.py` / `carbon.py` 确定性算出，AI 只负责**取数、推理、登记建议**。四个好处：

1. 数字可复算、可审计，不会出现「AI 编了个数」的情况；
2. 没有密钥、没有网络时系统仍然能完整演示（降级为离线模板，且同样产出结构化建议）；
3. 评测「技术质量」时，能清楚说明哪部分是模型能力、哪部分是工程确定性；
4. 模型拿到的每个数字都能追溯到某次工具调用的返回值——前端把调用轨迹直接展示出来，可现场验证。

## 2.1 工具调用循环（为什么这是「生成式 AI 实现」而非「套壳」）

`ai.py::_agentic_diagnose` 实现完整的 function calling 往返：

```
contents = [用户提示]
loop (最多 MAX_TOOL_TURNS = 8 次):
    resp = Gemini(contents, tools=[4 个 functionDeclarations])
    若 resp 含 functionCall:
        contents += [模型回合]
        contents += [工具执行结果]     # dispatch_tool 本地执行，纯计算，无副作用
        continue
    若 resp 含文本:  return 文本 + 累计的 actions / tool_calls
```

| 工具 | 输入 | 输出 | 为什么必须由工具提供 |
|---|---|---|---|
| `query_metrics` | `cloud?` / `pattern?` / `limit?` | 按金额降序的节点明细 | 防止模型自己「回忆」数字 |
| `estimate_carbon` | `energy_kwh` / `hour` / `region?` | 碳强度、碳排、当日最优时段 | 碳强度曲线是外部模型，模型无从知晓 |
| `simulate_defer` | `node` / `to_hour?` | 减碳量、减碳比例、前后强度 | 需要与 `analyzer` 的真实电耗联立 |
| `propose_action` | `title` / `detail` / 收益 / 成本 | 登记编号 `A1/A2/...` | 建议必须结构化才能渲染成决策按钮 |

`dispatch_tool` 的容错约定：未知工具名或参数异常**返回错误对象而不抛异常**，避免模型一次误调用就打断整个诊断。

## 3. 计算口径（全部假设显式声明）

设：`requested` 预留卡数，`used` 实际使用卡数，`H` 时长（小时），`U` 平均利用率（%）。

**浪费卡时**

```
申请未用卡时 = max(requested - used, 0) × H
低效折算卡时 = used × H × (1 - U/100)     仅当 U < 30
浪费卡时     = 申请未用卡时 + 低效折算卡时
```

**折算系数**

| 系数 | 取值 | 来源与说明 |
|---|---|---|
| 空转功率系数 | 0.25 | 业界经验值：闲置 GPU 功率约为 TDP 的 20%~30%，取中值 |
| 满负荷功率占比 | 1.00 | 利用率 100% 时按满 TDP 计；中间线性插值（`active_power_ratio`） |
| 工业电价 | ¥0.70 / kWh | 可配置，按实际账单替换 |
| 碳排因子 | 0.581 kgCO₂e / kWh | 全国电网平均排放因子（作为时段/区域系数的基数） |
| 低效阈值 | 30% | 低于此值判定为「低效运行」 |
| 空转阈值 | 5% | 低于此值判定为「长期空转」 |
| 成年树年固碳 | 18 kg | 用于把碳排换算成直观当量 |

> 负载侧电耗按 `used × H × TDP × active_power_ratio(U)` 计算，用于碳感知调度测算——
> 它衡量的是「这台机器实际花了多少电」，与「浪费了多少电」是两个独立口径。

**卡型参数**（`analyzer.py: GPU_SPECS`，可按实际台账替换）

| 卡型 | TDP (W) | 卡时单价 (¥) |
|---|---|---|
| H800 | 700 | 24.0 |
| H100 | 700 | 28.0 |
| H20 | 400 | 12.0 |
| A100 | 400 | 15.0 |
| V100 | 300 | 8.0 |

> 未识别的卡型统一走 `DEFAULT_SPEC`（400 W / ¥15），不会因脏数据让整个批次失败。

## 3.1 碳强度时段模型（`carbon.py`）

**物理依据**：电网的碳强度不是常数。正午光伏出力高峰时，清洁电力占比高，每度电的碳排最低；
晚高峰火电调峰时最高。因此**同样的电耗，在不同时段跑，碳排不同**——这是「碳感知调度」的立足点。

**模型形式**：

```
碳强度(h, region) = 0.581 × 时段系数(h) × 区域系数(region)     单位 kgCO₂e/kWh
```

时段系数为 24 点相对值，全天均值为 1.0：

| 时段 | 系数 | 说明 |
|---|---|---|
| 13:00（最优） | 0.82 | 光伏出力高峰，清洁电力占比最高 |
| 19:00（最差） | 1.10 | 晚高峰火电调峰 |
| 04:00~06:00 | 0.86~0.87 | 夜间基荷，波动小 |
| 09:00 | 1.00 | 接近全天均值 |

区域系数：`north 1.05 / east 1.00 / south 0.85 / southwest 0.55 / default 1.00`
（火电占比高的区域系数更大；西南水电富集，系数显著偏低）。

**为什么算「挪时段」而不是「少用电」**：消除浪费（少用电）和挪时段（同样用电但换时间）是两条独立的减碳路径。
前者省钱又减碳，后者不省钱但仍减碳，且**对生产无侵入**——不需要砍任务，只需要改调度时段。
示例数据下的实测输出：电耗最大的节点在 20:00 运行，挪到 13:00 后可减碳 54.7 kgCO₂e（约 25%），电耗与电费均不变。

> ⚠️ **诚实的边界**：这条曲线与区域系数是公开资料的**简化近似，不是实测数据**。
> 要作为真实调度依据，需接入 Electricity Maps 等实时碳强度数据源；`carbon.py` 的对外接口已按可替换设计，
> 替换数据源不影响 `ai.py` 与前端。此外，只有具备 checkpoint 续训能力的任务才真正可延后，
> 本项目把「可延后性」列为待补数据，没有假设所有任务都能平移。

## 4. 已知限制

1. **能耗用 TDP × 空转系数近似**，不是实测功耗。要精确需要接入 DCGM / IPMI 功耗读数。
2. **利用率按周期平均**，会掩盖「前 80% 时间满载、后 20% 空转」这类分布问题。
3. **未做任务级归因**——知道哪个节点浪费，但不知道是哪个任务造成的。补任务队列与卡分配的关联数据后可升级。
4. **电价是常量**，真实账单是非线性阶梯电价。
5. **碳强度时段曲线与区域系数是简化近似，非实测**（详见 3.1 节的边界说明）。
6. **未验证「负载可平移性」**：碳感知调度成立的前提是任务可延后，本项目未对任务做可延后性判定，
   因此相关建议在 UI 与文档中均标注为「需人工确认」。

## 5. 升级路径

| 阶段 | 动作 |
|---|---|
| 近期 | 接入真实监控导出（Prometheus / 云 API），替换示例数据 |
| 近期 | 接 DCGM 功耗实测值，把空转系数换成实测曲线 |
| 近期 | 接入 Electricity Maps 实时碳强度，替换近似时段曲线（接口不变） |
| 中期 | 增加任务维度，实现逐任务归因，并判定任务可延后性 |
| 中期 | 迁移到 Vertex AI + Gemini，使用托管部署与 IAM 鉴权替代 API Key |
| 远期 | 从「事后审计」升级为「事前预测」：在配额审批环节预估浪费风险 |
