## 1. 问题定义

训练集群上最贵的误判不是「漏报」，而是**方向搞反**。两个方向都真实存在：

| 误判 | 表现 | 代价 | 公开资料的说法 |
|---|---|---|---|
| **把应用 bug 当硬件故障** | 看到 Xid 13 / 31 / 43 就去报修 | 一块好卡被下线、走 RMA、集群容量白掉 | 「不要为用户的 bug 去报修一块好卡」——Xid 13/31/43 会**跟着有 bug 的任务走**，换节点仍然复现，而硬件是好的 |
| **把硬件劣化当偶发** | 看到 Xid 94 就说「重启一下就好」 | 劣化持续累积，等 Xid 95 出现时影响面已经扩大 | 单次事件往往无害，**速率变化才是信号** |

这两种误判**用同一个错误码就能触发**（案例库里 `case-xid94-single` 与 `case-xid94-rising`
就是同一个 Xid 94、同一张卡型、结论相反）。所以判别依据不可能是码本身，只能是：

1. **趋势** —— 30 天频次是否上升、可纠正 ECC 是否同步上升；
2. **因果链** —— Xid 45 / 154 这类码本身**只描述后果**，把它们当根因会一路查错方向；
3. **内核与进程状态** —— 有 Xid 62 或进程处于 D 状态 → 查驱动/硬件；零 Xid 且进程在 futex 等待 → 查代码。

传统监控只回答「Xid 是多少」，不回答**「该不该换卡」**。本项目补的就是这一步，并且把答案压缩成两个
**能被当场证伪的字段**：

- **六分类**：`application` / `hardware` / `hardware_watch` / `environment` / `config` / `network` /
  `undetermined`
- **是否报修**（`should_rma`）：一个布尔值

**分层原则**：所有**事实**由 `kb.js` / `triage.js` 确定性给出，AI 只负责**取证、推断、登记**。
四个好处：

1. 数字可复算、可审计，不会出现「AI 编了个数」；
2. 模型不可用时系统仍能完整演示（降级为规则路径，且同样产出结构化建议）；
3. 技术评审时能清楚说明哪部分是模型能力、哪部分是工程确定性；
4. 模型拿到的每个数字都能追溯到某次工具调用的返回值 —— 前端把轨迹直接展示出来，可现场验证。

## 3. AI 层：工具调用循环

```
contents = [提示词]
loop（最多 MAX_TOOL_TURNS = 12 轮）:
    resp = Gemini(contents, tools=[本模式的 functionDeclarations])
    若含 functionCall:
        contents += [模型回合]            # 原样回传 parts，保住思考模型的 thoughtSignature
        contents += [工具执行结果]        # 角色是 user，不是 function，见 3.1
        continue
    若含文本: return 文本 + 累计的 tool_calls
    两者都无: 抛错（把已完成的调用挂成 resume）
```

### 3.1 contents 的角色纪律

| 段 | role | 说明 |
|---|---|---|
| 用户提示 | `user` | 初始输入 |
| 模型发起的工具调用 | `model` | **原样回传** `parts`，不重建 —— 思考模型返回的 `thoughtSignature` 必须保持不动 |
| 工具执行结果 | **`user`** | 见下 |

**为什么工具结果的角色是 `user` 而不是 `function`**（这是踩出来的，不要再试）：

- 新版模型已不接受 `function`，服务端报
  `400 Role 'function' is not supported. Please use a valid role: SYSTEM, USER, ASSISTANT, …`；
- 改用 `user` 回传本来是对的，却会被官方 JS SDK 的客户端校验拦住
  （`Content with role 'user' can't contain 'functionResponse' part`）。

两条路都被堵死，所以 `ai.js` **直接打 REST**，自己控制 `contents` 的角色，顺带去掉 150KB 依赖。
实测（`scripts/probes/probe_tool_roundtrip.py`）：回传角色 `function` 时只有
`gemini-3.1-flash-lite` 还能兼容；回传 `user` 时 `gemini-3.5-flash-lite` / `gemini-3.5-flash` /
`gemini-3.1-flash-lite` 全部通过。

> 鉴权只能用 header `x-goog-api-key`。用查询参数 `?key=` 会被边缘直接返回 HTML 400，
> 看起来像「模型不存在」，极易误判成模型下线。

### 3.2 轮次上限与续跑

**★ 一轮 ≠ 一次调用。** 模型可以在一轮里并行发多个 `functionCall`（实测它会一次发 4 个
`inspect_node` 逐个节点取证），所以 `MAX_TOOL_TURNS` 对应的是**来回次数**。

值取 **12**。为什么不是 8：值班巡检跑完一整套（扫描 → 逐节点取证 → 查库 → 止损 → 建单 → 通知 → 报告）
在模型不并行、一次只发一个调用时要 **13 轮**，定 8 会**必然截断**；而截断的代价是换模型后从头再来一遍
—— 更慢、更贵，而且会**多扫一次集群**。

**续跑（resume）机制**：上游 5xx 时，把 `{ contents, toolCalls, turns }` 挂到错误对象上，
`tryModelChain` 跨模型携带它**接着跑而不是从头再来**。上限 `MAX_RESUMES = 2`。

挂 resume 的条件被刻意限制为两类：

| 场景 | 是否挂 resume | 原因 |
|---|---|---|
| 传输 / 上游失败（请求没成功） | ✅ 挂 | 这一轮没产生任何状态，重试无副作用 |
| 撞轮次上限，且**已有已完成的调用** | ✅ 挂 | 判断标准是「有已完成的调用就值得带走」 |
| 模型绕圈不收敛、一次调用都没有 | ❌ 不挂 | 接着跑只会继续绕，白烧配额 |

**线上实测踩到的原始故障**：巡检第一轮跑了 13 次调用后撞上限，因为当时没挂 resume，整段被丢弃，
换模型后从头又扫了一遍集群。症状藏在界面上 —— **引用表有 T1…T18，调用轨迹却只显示 5 条**，
`T14 = scan_cluster` 出现第二次扫描。「证据链」和「实际做过的事」对不上，而这恰恰是整套东西最核心的卖点。

### 3.3 模型降级链与两种 429

免费层每个模型的日配额独立，所以按
`gemini-3.5-flash-lite → gemini-3.5-flash → gemini-3.1-flash-lite → gemini-3.8-flash`
依次尝试。代码区分两种 429：

| 情况 | 判据 | 处理 |
|---|---|---|
| 短时限流 | 建议等待 ≤ 90s | 等一下重试**同一个模型**（最多 2 次） |
| 当日配额耗尽 | 响应里写 `retry in 18h44m` | **立刻换模型** —— 干等等于把界面卡死十几小时 |

换模型的原因会如实显示在界面上（`degraded` 字段），不假装一次就成功了。

### 3.4 结果的唯一出口

`diagnose` 与 `patrol` 都必须走 `finishResult(state, mode, text, extra, error)`。这个函数**整包
spread、不挑字段**。它存在的理由是一个真 bug：两个入口原先各自写了一个局部 `finish()`，长这样 ——

```js
packResult(state, { mode, text, model: extra.model || '', error });
if (extra.degraded) out.degraded = extra.degraded;
```

也就是**只把 `model` 与 `degraded` 挑出来**。于是 `tool_calls` 被静默丢掉：模型明明调了
`lookup_xid` / `inspect_node`（`citations` 里一条不差地记着），界面上「AI 的工具调用轨迹」却永远显示
「本次没有调用工具」。**被藏起来的恰恰是整个演示最值钱的证据。** 更糟的是同一屏上
「由 gemini-… 自主调用工具生成」还在说真话，两处自相矛盾。

`finishResult` 里还写了两条**不变量检查**，违反就把 `pipeline_error` 显式暴露到界面上：

```js
// 在线路径的形状保证：runAgent 从 `const toolCalls = []` 起手，所以它一定返回数组。
// mode 是 gemini 而 tool_calls 不是数组，只有一种解释 —— 打包又漏字段了。
const broken = mode === 'gemini' && !Array.isArray(extra.tool_calls);

// 第二条：每条引用都对应一次工具调用。引用是工具真跑的时候登记的，一次调用最多一条，
// 所以「引用数 > 调用数」在数学上不可能 —— 出现了就说明有一批调用记录丢了。
const lostWork = (state?.citations || []).length > calls.length;
```

## 4. 模式即能力边界（不只是提示词差异）

应用有两个入口，它们的差别**不止是措辞，而是工具集本身**：

| | 单次分诊 `diagnose()` | 值班巡检 `patrol()` |
|---|---|---|
| 输入 | 用户贴的一段失败现场 | 一个空证据包 + 一整个集群 |
| 工具数 | **6** | **10** |
| 多出来的工具 | — | `scan_cluster` / `execute_action` / `draft_ticket` / `notify_operator` |
| 终态 | 判断 + 方案 + 执行包 | 判断 + **真的动手** + 建单 + 触达 |

`tools.js: toolSpecsFor(mode)` 做裁剪，`prompt.js: hardRules(mode)` 按模式生成硬约束。

**为什么要裁剪**：单次分诊**根本没有连集群**。给它 `execute_action` 这类工具不但没用，还会让模型白调
一次、收到一句「当前会话没有连接集群」，在调用轨迹上留下一行看着像故障的记录。
第一次跑浏览器验收时就真出过这个：单次分诊里模型调了 `notify_operator`，拿回「无法投递通知」。

> **给模型一把开不了门的钥匙，责任在设计，不在模型。**

反过来，**提示词必须与实际声明的工具集一致**。`hardRules(mode)` 是函数而不是常量，原因就在这里：
如果写死「调用 `propose_fix` / `execute_action`」，单次分诊的提示词就会去指点模型用一个它根本没有的工具，
模型的第一次尝试就注定是错的。

## 5. 知识库层（`kb.js`）

**为什么把全部事实集中在一个文件里**：分诊器的全部可信度来自一件事 ——
**结论必须能落到一条可核实的事实上**。所以每条事实都带 `source` 字段指向权威出处
（NVIDIA Xid 文档 / GPU 调试与内存错误管理指南 / 公开集群 RAS 知识库 / PyTorch 与 CUDA 官方兼容表）。
模型只能通过工具读到这些事实，读不到就无权下结论 —— **这比写「请勿编造」的提示词有效得多。**

| 内容 | 规模 | 说明 |
|---|---|---|
| Xid 表 | **24 条** | 每条含含义、故障归类、严重程度、推荐处置、是否需要 RMA、出处 |
| 故障特征签名 | **27 条** | 非 Xid 类报错（OOM、NCCL 超时、驱动掉线、GPU 卡死……），带正则 + 典型根因 + 该核实什么 |
| 诊断原则 | **6 条** | 首发原则 T0 / 次生事件不是根因 / 症状 ≠ 根因 / 趋势优先于快照 / 不要混为一谈 / 应用故障不要走报修 |
| 版本矩阵 | 3 张表 | torch↔CUDA、CUDA↔最低驱动、驱动↔CUDA 上限 |
| 显存规格 | 14 个型号 + 别名 | 用于显存核算 |

几条**刻意的设计**：

- **`class_hint` 是默认倾向，不是结论。** 工具返回时会明确标注这是 hint，要求模型结合
  `lookup_xid` / `inspect_node` / `check_compat` 再定性。
- **分歧要写出来，不要抹平。** Xid 43 的归类在各权威资料间**存在分歧**（NVIDIA 运维知识库与阿里云 ACK
  判为应用问题；另一份开源诊断表判为硬件/驱动）。知识库把这个分歧原样记下，并写明
  「遇到 43 必须回查同一时段是否还有 48 / 95 / 79 这类硬指标：有则按硬件处理，无则按应用处理」。
  **这不是知识库的缺陷，而是分诊必须存在的原因。**
- **有条件的处置要标注前提。** Xid 62 的动作写的是「若与 Xid 79 同现或反复出现，升级为硬件方向排查」，
  `rma: null`。这个前提是踩过一次才补上的：值班提示词最初只让模型 `inspect_node` 取证、没让它查库，
  于是模型凭印象把 Xid 62 当成硬件报废，给一张**本不该报修**的节点建了 RMA 工单。修法是两处一起改 ——
  `PATROL_TASK` 里补上「遥测里出现的每一个 Xid 码都要调 `lookup_xid`」，`DIAGNOSTIC_DISCIPLINE` 里补上
  「有条件的处置」纪律。**漏查一次知识库，代价是让一张还能用的卡下线。**

## 6. 确定性预分析层（`triage.js`）

纯函数、零依赖、可在 Node 里直接单测。它产出两样东西，**并且严格要求把两者分开**：

| 产出 | 性质 | 给谁 |
|---|---|---|
| `confirmed` | **已确证事实** —— Xid 及出现次数、命中的特征、版本栈是否自洽、显存需求与容量 | 提示词里单列一节，并注明「由确定性代码算出，无需你重新计算」 |
| `hints` | **倾向性提示** —— 各来源对分类的加权投票 | 提示词里明确标注「这是机器投票的结果，不是结论。若你调取的证据与之冲突，以证据为准」 |

这个区分不是形式主义：如果把投票直接说成结论，模型就会照抄，整套东西退化成查表 ——
而 F8 基准已经证明查表是不够的。

同一个文件里还有 `ruleBasedTriage()`，它**只做最朴素的两步**：取投票最高的分类；分类是 `hardware`
就建议报修。它同时被三处使用：

1. **F8 基准的对照物**（见第 9 节）；
2. **离线降级路径**（`offlineCaseTriage`）；
3. `verify_triage.mjs` 的可复现数字来源。

> ⚠️ **如果要让基线表现更好，不要改这个函数** —— 那等于把对照物也变成 AI。
> 正确的做法是把它当成「朴素规则能达到的上限」，如实报告它错在哪几题。

## 7. 工具层（`tools.js`）

**设计意图一句话：分诊最怕的不是模型不够聪明，而是模型太聪明地编造。**
所以 10 个工具全部只做一件事 —— **返回证据**。它们从不返回结论，也从不返回「建议分类」。

| 工具 | 模式 | 输入 | 输出 | 为什么必须由工具提供 |
|---|---|---|---|---|
| `search_failure_signature` | 分诊 | `query` | 候选模式 + 典型根因 + 应核实项 | 防止模型自己「回忆」故障模式 |
| `lookup_xid` | 分诊 | `code` | 权威含义、归类、处置、是否 RMA | 知识库是外部事实，模型无从知晓 |
| `check_compat` | 分诊 | driver / cuda / torch / nccl | 逐条核验结果 | 版本矩阵是硬规则，需精确比对 |
| `estimate_memory` | 分诊 | 训练配置 | 显存需求区间 + fit 判定 | 需要精确计算，模型算不出来 |
| `inspect_node` | 分诊 | `node` | 遥测：Xid 序列、ECC、降频、PCIe、30 天历史 | **判断「偶发还是劣化」的唯一依据** |
| `propose_fix` | 分诊 | `action_id` + 结论字段 | 登记一条建议 | 建议必须结构化才能渲染成决策项 |
| `scan_cluster` | 值班 | `include_healthy?` | 需要关注的节点清单（**现象**） | 主动发现的入口 |
| `execute_action` | 值班 | `node` / `action_id` / `reason` / `params` | 执行结果 + **回验结论** | 执行必须落在一个能被审计的地方 |
| `draft_ticket` | 值班 | 工单字段 + `evidence_refs` | 草稿工单 id | 高风险动作的产物是工单 |
| `notify_operator` | 值班 | `node` / `title` / `text` | 投递结果 | 主动触达 |

### 7.1 引用编号：把「可溯源」变成看得见的东西

`ToolState._cite(source, payload)` 在每次工具真正执行时登记一条引用，返回 `T1` / `T2` / …
模型在 `propose_fix` / `draft_ticket` 里引用它，前端就能把每条建议连回产生它的那次调用。

模型编造的引用会被**丢弃并回告**：

```js
const validRefs = evidence_refs.filter((r) => this.citations.some((c) => c.ref === r));
// droppedRefs 会写进返回值，告诉模型「只能用工具返回值里出现过的 ref」
```

### 7.2 参数白名单同时是安全边界

`TOOL_PARAMS` 只取白名单里的字段。模型偶尔会多传参数（**甚至试图传一个 `risk` 来给动作重新定级**），
不在表里的字段**连进都进不来**。

**★ 这张表刻意不写方法名**：`ToolState` 上的方法名与工具名保持完全一致，分发时直接用工具名当方法名。
原来写成 `{ 工具名: [方法名, 白名单] }`，于是同一个名字要维护两份（`lookup_xid` 与 `lookupXid`），
一旦改了一处忘了另一处，`dispatchTool` 的 try/catch 会把它吞成一句「工具报错了」——
模型只看到「这个工具坏了」，真因藏在分发表里，靠读代码几乎发现不了。
**六个工具里有五个当时就是坏的**，直到自检脚本逐个去比才暴露出来。现在这种错位在结构上不可能出现。

### 7.3 工具异常不中断会话

`dispatchTool` 捕获异常并把它当成一次**有信息的失败**返回给模型（`{ error: ... }`），
不打断整个诊断。代价是它会吞异常 —— 所以工具名与方法名必须由结构保证一致（见 7.2）。

## 8. 执行层：审批与回验

### 8.1 三级风险由**爆炸半径**决定，不由难易决定

| 风险 | 判定规则 | 审批要求 | 数量 |
|---|---|---|---|
| **低** | 只影响当前任务进程、可逆、不碰硬件与系统 | **一键批量批准** | **6 条** |
| **中** | 影响节点上其他任务，或需要短暂中断 | **逐条批准 + 勾选影响面确认** | **5 条** |
| **高** | 不可逆、涉硬件资产、跨节点或影响他人 | **逐条批准 + 必填变更单号与审批人 + 二次确认** | **3 条** |

判定看的是爆炸半径而不是难不难做：**装个 wheel 可能很麻烦，但它只影响一个容器，所以是低风险；
重启节点只是敲一行命令，但它会杀掉别人跑了一周的任务，所以是中风险。**

另有 **1 条被系统标记为「不建议」** 的动作：`raise_nccl_timeout`（调大集合通信超时）。
知识库写明它是**掩盖问题而非解决问题** —— 它让失败从「30 分钟报超时」变成「2 小时报超时」，
根因一个都没少，只是发现得更晚。动作库保留它、界面上灰显展示，但**不放进给模型的候选清单**。
让系统能明确地说「这条路我们知道，但不建议」，比假装它不存在更有主见。

### 8.2 ★ 风险等级不从模型来

动作库里每个动作**自带** `risk` 字段，模型只能**选用**（传 `action_id`），不能**自定**等级。
落点在 `tools.js` 的两处：

```js
// ① execute_action：只有 low 会被真正执行
if (act.risk !== 'low') {
  return { refused: true, error: `「${act.label}」是${lv.label}动作…你无权直接执行。`,
           instead: '请用 propose_fix 登记这个动作…交给人工审批流' };
}

// ② propose_fix：登记时从库里取风险等级，不读模型任何字段
const action = { risk: act.risk, risk_label: RISK_LEVELS[act.risk].label, approval_requirement: … };
```

**★ 顺序很重要：安全规则优先于可用性检查。** 这个顺序是自检脚本逼出来的 —— 原先「有没有连接集群」
的检查排在风险检查前面，于是没连集群时模型收到的是「没有连接集群」，而不是「这个动作你没权限执行」。
在真实值班场景里，模型看到前者会以为**连上再试一次就行了** —— 它会把审批门槛误读成环境问题。
**审批是规则，规则必须先说。**

### 8.3 模拟集群后端（Firestore）：让「执行是真的」

**为什么必须有这个后端**：如果「执行」只是界面上把按钮变灰、把文案改成「已处理」，
那它和一份 PPT 没有区别，评委一眼就能看穿。所以这里放一个**有真实状态的模拟集群**。

| 集合 | 用途 |
|---|---|
| `cluster` | 6 个节点的状态与遥测（`cordoned` / `schedulable` / `draining` / `jobs` / `telemetry`…） |
| `events` | **操作日志**：每条记录含 `before` → `fields_written` → `after` → `verified` |
| `tickets` | 工单草稿（`status: 'draft'`） |
| `notifications` | 通知队列（`status: 'queued'`） |

安全规则**匿名可读写**，因为浏览器端没有登录流程 —— 这是明确的安全边界，不是疏漏；
开放面被规则锁死在这 4 个集合内，其余路径一律拒绝。`scripts/fb_firestore_setup.py` 负责
`check` / `rules` / `seed` / `verify`。

**动作对状态的真实作用**写在 `cluster.js` 的 `EFFECTS` 表里，每条动作三段，缺一不可：

```js
cordon_node: (n) => ({
  fields: { cordoned: true, schedulable: false },                       // 真的会落库
  verify: (a) => a.cordoned === true && a.schedulable === false,        // 拿什么判定它生效
  describe: `禁止 ${n.node} 接新任务；节点上 ${(n.jobs||[]).length} 个正在运行的任务未受影响`,
}),
```

**没有 `verify` 的动作不允许被登记** —— 因为「执行了但没验证」等于没执行，只是换了个地方写日志。
幂等性也是要求：巡检可能重复触发同一个动作，重复 `cordon` 不会报错、也不会产生第二条重复语义的记录。

**执行 → 回验的完整链路**（`executeAction`）：

```
before = getNode(node)            # 执行前状态
planned = effect(before, params)  # 算出要写什么
after  = patchNode(node, fields)  # ★ 真的写进 Firestore（updateMask，不清掉其它字段）
verified = planned.verify(after)  # ★ 自己读回来确认
写 events（status: ok | unverified | error）
```

回验失败时事件写 `unverified`，界面显示「回验未通过」。
**宁可显示一条失败的动作，也不要谎报成功** —— 演示里的假成功，在评委追问一句「数据真的变了吗」
时就会崩。

### 8.4 报修只建草稿，不提交

`file_rma` 是高风险：走一次 RMA，集群就少一块卡。所以 `draft_ticket` 只建 `status: 'draft'` 的工单，
把证据、命令、序列号位置、判断依据全部填好，让**人只需要点确认**。草稿里
`approved` / `ticket_no` / `approver` 三个字段**只能由人在界面上填写** —— 那是人签字的痕迹。

这条不是能力缺失，是产品判断：**低风险它自己动手，高风险它把门槛降到最低但把决定留给人。**

## 9. 反幻觉的四条纪律

整套东西的设计可以压成四条纪律，每条都同时落在**提示词**与**代码**两处：

| 纪律 | 提示词里怎么说 | 代码里怎么保证 |
|---|---|---|
| **数字只能来自工具** | 「工具没给你的数字，你的答案里就不该出现」 | 显存/版本由精确计算给出；引用编号只能来自 `citations`；编造的 ref 被丢弃并回告 |
| **风险等级不可协商** | 「你不能声明或修改动作的风险等级」 | `execute_action` 只放行 `risk === 'low'`；`TOOL_PARAMS` 白名单让模型连 `risk` 字段都传不进来 |
| **查不到就说查不到** | 「编一个听起来合理的解释，比直接说『不知道』糟糕得多」 | 知识库查不到时返回「无记录，不得推测」；`permanent` 之外一律归入 `undetermined` |
| **工具一旦给结论，分诊就退化成查表** | —— | `nodeSignals()` / `scan_cluster()` 只描述现象，绝不给分类 |

> 为什么两边都要写：**只写在提示词里是「可以被说服的」，只写在代码里模型会因为不理解边界而反复撞墙。**
> 两边都要有，但**最终生效的是代码**。

## 10. F8 基准：为什么必须用模型（可复现的对照）

「这件事规则做不好、必须上模型」是一个**可证伪的论点**，所以必须真的跑一遍去证伪它。

`scripts/verify_triage.mjs` 用**纯规则路径**把全部 **14 个**案例跑一遍。实测结果（可直接复跑）：

```
规则基线准确率（分类 + 是否报修全对）：11 / 14　（78.6%）
  仅看分类：11 / 14　仅看是否报修：12 / 14
```

| 案例 | 期望 | 规则给出 | 规则读不出的东西 |
|---|---|---|---|
| `case-xid48-dbe` | hardware + 报修 | application | Xid 45 是「前序错误的后果」，把它当根因会查错方向 |
| `case-xid94-rising` | hardware + 报修 | hardware_watch | 与 `case-xid94-single` 同一个码、同一张卡型，判别依据是趋势 |
| `case-gpu-hang-deadlock` | application | network | 与 `case-gpu-hang-xid62` 都是「训练卡死」，判据是内核是否干净、进程是否 D 状态 |

**只比两个字段**（`class` 与 `should_rma`），理由是它们是**能被当场证伪的布尔值**，
比一比「叙述写得好不好」客观得多。

案例库的规模与分布也是设计出来的：

```
案例总数：14　需要报修：4 个　不需要报修：10 个
分类分布：配置 2　网络 1　应用 2　环境 4　硬件 4　观察 1
成对对照：Xid 94（偶发 vs 上升）｜ 驱动掉了（版本不匹配 vs 掉卡）｜ GPU 卡死（有 Xid 62 vs 内核干净）
```

> ⚠️ **诚实性约束**：基准表的数字必须来自实际运行。跑出来是 11/14 就写 11/14，并说明错在哪几题。
> 伪造准确率是最容易被现场戳穿的事。所以 `verify_triage.mjs` 的注释里写着
> 「这个数字是会写进 deck 和界面的，所以它必须来自实际运行，不能由人凭感觉填」。
> AI 分诊那一侧的数字同理 —— 由页面跑满 14 个案例后自动统计，未跑满则显示为空。

## 11. 工程验证方法论：三个脚本，各自挡住一类 bug

| 脚本 | 断言数 | 它**唯一**能挡住的东西 | 为什么不能用别的代替 |
|---|---|---|---|
| `verify_triage.mjs` | 全部通过 | 动作库不变量、审批门槛是否拦得住、模型能否绕过风险等级、案例库结构 | 不跑链路，也不碰浏览器 |
| `verify_pipeline.mjs` | **81 / 81** | **`tool_calls` 被静默丢弃**这类链路字段丢失 | 靠读代码发现不了（两个 `finish()` 相隔一百多行、写法完全一样）；靠不变量校验也发现不了（它不跑链路） |
| `browser_check.mjs` | **31 / 31** | 界面能跑起来、控制台无「我方」错误、执行真的落库 | `app.js` 顶层就调 `init()`，全是 `document.querySelector`；Node 里**模块解析成功 ≠ 界面能跑** |

三个脚本的分工是有意的：

- `verify_pipeline.mjs` 用**桩 fetch + 内存假集群**，不需要网络、不需要 Firestore、不消耗模型配额，
  因此可以高频跑；
- `browser_check.mjs` 用**真 Chrome + 真 Firestore**，是唯一的端到端验收。
  它不能用 `--dump-dom` 代替 —— 那只能看到最终 HTML，看不到控制台异常，
  而「某个 import 路径写错导致整块标签页空白」这类静默失败会漏。

三个跟测试有关的、值得记下来的教训：

1. **假对象的形状必须跟真东西一致。** 写假集群的 `event` 时漏了 `verified` 字段，
   于是 P2 报「回验字段没带出来」—— 查下去才发现真代码是对的、假对象是错的。
   **假对象形状跟真东西不一致，测试就在证明一个不存在的事实。**
2. **静态护栏要先剥注释再匹配。** P0 段用正则禁止「手写 `packResult(state, { mode, text, model:`」这种写法，
   结果匹配到了 `finishResult` 文档注释里**故意引用的那句坏写法**作为反例，第一次跑就报了假警。
3. **一条总是红的检查等于没有检查。** 上游 Vertex AI 返回 500 是**我们处理掉的现实条件**，
   不是我们的代码出问题；但浏览器仍把它记成控制台 error。所以断言只查「我方」错误，
   上游失败单独统计并如实打印（不藏起来）。

## 12. 已知限制

1. **知识库只覆盖 24 条 Xid 与 27 条特征签名**，不是全部 100+ 个 Xid 码。
   这不是偷懒，是设计：**知识库的边界就是模型的能力边界**。
2. **AI 分诊的准确率不是我们自己声明的**，由页面自动统计，未跑满即为空。
   规则基线 **11/14** 可当场复现（本地、秒级、不耗配额）。
3. **修复动作的命令按通用工具口径给出**，不绑定某一种调度器；凡涉及集群平台的部分都在 `note` 里写明
   「按你的平台替换」。**宁可写清楚要替换，也不假装一条命令能通吃所有集群。**
4. **执行包不含任何自动执行能力**：命令需要人工复制到目标节点执行。一份执行包里最危险的东西不是
   写错的命令，而是**没被批准却被执行**的命令 —— 所以没有回滚方案的动作不允许进执行包，
   未获批准的动作明确标注「未批准，请勿执行」。
5. **「主动」在演示里的真实含义**：本应用是纯静态站点，没有常驻进程，所以值班巡检是
   **由人点一下开始、之后自动跑完**的循环。真实部署应由 Cloud Scheduler 之类定时触发 —— 界面上写清楚了。
6. **通知只入队，不真发**：落到 `notifications` 集合、状态保持 `queued`。真实部署需接入 IM / 邮件。
7. **免费层配额是演示期最硬的约束**（2026-10-14 实测）：一次巡检约 12–16 次模型请求，
   单模型免费日配额约 20 次 → **一天约够跑 5–6 次巡检**。单次分诊有本地缓存（命中零请求），
   值班巡检没有缓存。
8. **上游偶发 5xx 会触发续跑（上限 2 次）**，界面会显示「上游失败过一次，已带进度续跑」；
   连续失败超过上限仍降级到规则路径。
9. **界面与提示词目前是简体中文**；这是纯前端应用，没有对外 API 面受影响。英文 UI 是明确的后续项。
10. **不接入任何真实生产集群**：案例是构造的、节点是模拟的。真实的腾讯云 / 阿里云 / 百度云 /
    智星云集群与 Google Cloud 之间没有网络通路，架构上也够不着。迁移的只是方法论，不是数据。

以上限制在技术评审环节会被问到，本文档直接列为已知边界而非回避。

## 13. 升级路径

| 阶段 | 动作 | 卡在哪 |
|---|---|---|
| 近期 | 接监控系统 webhook，把失败任务自动灌进分诊入口 | 需要常驻后端与生产凭据；本应用是纯静态站 |
| 近期 | 把 `inspect_node` 的模拟数据源换成 DCGM / `nvidia-smi` 的真实导出 | 需要生产侧采集器与凭据 |
| 近期 | 通知渠道接飞书 / 企业微信 / 邮件 | `notifications` 集合的结构已按此设计 |
| 中期 | **误报修率看板**：统计「本季度避免了 N 次不必要的 RMA」 | 需要历史数据回流。**这是把技术价值翻译成钱和集群容量最直接的一页** |
| 中期 | 把动作库的 `EFFECTS` 换成真调度器的 API（K8s / Slurm） | 需要先在非生产集群做灰度 |
| 中期 | Firestore 换成基于 Auth 的安全规则 + 强制 App Check | 需要登录流程；当前是匿名规则 |
| 远期 | 集群级根因聚类：100 个失败任务聚成 5 个根因 | 需要聚合层与任务元数据 |
