AI 的工具调用轨迹

所有数字都由这些工具从确定性代码中取出，模型无法凭空生成。 每条处置建议都带引用编号（如 T2），可指回产生它的那次调用。

    处置清单

    风险等级由动作库决定，不由模型判断。 模型只能选用动作（传 action_id），不能声明或修改等级 —— 所以它无法把一个高风险动作说成低风险来绕过审批。 低风险可批量批准；中风险需逐条批准并勾选影响面；高风险须填变更单号与审批人。

    这个数字是怎么来的
    
        
    
          
    
            规则基线刻意只做最朴素的两步：取预分析投票最高的分类，分类为 hardware 就建议报修。
            这正是真实世界里的常见做法 —— 看 Xid 码查表。它会错在两类案例上：
            需要读 30 天趋势的与需要区分次生事件与根因的，
            这两类恰好是模型能做、规则做不好的。
            

    
            数字由 scripts/verify_triage.mjs 与页面上的本地计算共同产出，
            两者跑的是同一份代码。我们不上报任何跑不出来的成绩 ——
            如果规则基线是 11/14，页面上写的就一定是 11/14。
          
    
        
    
      
    
    
    

    
    
    

      
    
        
    
          
    动作库与审批

    运行方式
    
      
    
        
    
          本页面是纯静态站点，托管于 Firebase Hosting：分诊逻辑在浏览器内运行，
          Gemini 通过 Firebase AI Logic 直连调用（密钥由平台托管）。
          值班模式下的集群状态读写走 Cloud Firestore。
          即使模型不可用，页面也会自动降级为离线规则路径，功能完整可演示。
          

    
          本应用不接入任何真实生产集群：分诊用的案例是构造的，值班用的节点是模拟的。
          真实的腾讯云 / 阿里云 / 百度云 / 智星云集群与 Google Cloud 之间没有网络通路，
          从架构上也够不着 —— 这一点写在仓库 README 里。
